# FruitDefense 游戏策划总纲

本文描述 FruitDefense 要做成什么，以及各系统之间长期稳定的设计关系。它不记录构建哈希、SDK 安装状态、逐项验收日志或某次实现的任务进度。

## 0. 首要实现约束

- **已定**：面向策划、美术日常使用的 Unity 编辑器工具、自动化验收代码和一次性诊断工具必须明确分层。实际工具只暴露稳定工作流；自动化验收放在独立测试目录和统一验证入口；一次性 runner、临时导入器与任务专用调试菜单在验收完成后必须删除，不得长期混入实际工具。
- **已定**：测试夹具、验收关卡和诊断生成物不得进入生产 `Resources`、正式关卡目录、发布清单或 release scene。测试只能从 Editor 测试目录显式加载或注入，且不得改变 Lobby 的正式可玩内容、运行时回退规则或发布结果。

## 文档状态标记

- **已定**：已经形成明确方向，后续需求默认遵守。
- **方向**：当前认可的产品方向，细节仍需通过后续策划或 OpenSpec 变更确定。
- **当前基线**：已经存在的玩法或结构，但不自动等于永久设计。
- **待定**：尚未做出策划决定，不能由当前实现反推结论。

## 1. 游戏定位

- **已定**：竖屏、轻量、单人 PVE 水果塔防。
- **已定**：核心操作围绕刷新水果、花盆种植、阵型调整、同类合成和装备组合展开。
- **已定**：发布平台顺序为抖音小游戏优先，微信小游戏后续；普通 WebGL 是共同构建与验收基线，不代表任一小游戏平台已经适配完成。
- **方向**：让玩家用较少的操作完成连续而有反馈的构筑选择，并能快速理解一次失败来自阵容、站位、资源还是波次压力。
- **待定**：目标用户画像、目标单局时长、单日推荐局数和正式难度曲线。

## 2. 核心体验支柱

### 2.1 构筑选择清晰

水果定位、星级、装备效果、花盆状态和可放置目标必须在竖屏空间中可辨认。玩家应该知道一次操作会种植、移动、交换、合成、安装装备还是扩建花盆。

### 2.2 组合有变化但边界明确

水果提供基础战斗角色，装备修改或补充能力，星级放大已有价值。组合系统允许内容扩展，但不依赖任意脚本、无限嵌套效果或玩家无法预判的隐藏规则。

### 2.3 战斗节奏可控

玩家能主动开始波次，并通过暂停和倍速控制观察与推进节奏。波次之间应留出处理阵容、奖励和下一波准备的清晰窗口。

### 2.4 结果可复盘

相同会话输入、随机种子和内容版本应产生可复现的战斗结果。表现可以丰富，但不能反向改变战斗规则。

### 2.5 战斗反馈可信

- **已定**：攻击蓄力、释放、弹道、接触、受击与击杀反馈必须围绕真实战斗时点组织；不能在伤害已经结算后再播放看似决定伤害的落地或命中动作。
- **已定**：普通受击闪白、挤压、后坐、飘字、震动和音效属于表现，不得默认改变敌人移动、目标选择或伤害结果。冻结、眩晕、击退等会改变战斗结果的控制必须作为明确、可验证的玩法效果单独配置。
- **方向**：轻击、重击、范围攻击、持续伤害、控制触发和击杀形成可区分但不过载的反馈层级；倍速和高密度战斗下允许表现层合并、限流或降低低优先级反馈，但不能丢失战斗规则事件。
- **已定**：战斗飘字使用有限的普通伤害、重击、持续伤害、资源、控制和击败语义角色。角色统一决定正式字体、最小字号、填充与描边、接触回弹、停留、上浮、渐隐和密度优先级；具体技能不得自行硬编码字体、颜色或另一套运动语言。
- **已定**：飘字颜色不是唯一语义线索，正负号、短文案、字号和节奏必须在弱化色相后仍能区分伤害、资源、控制和击败。最终可读性以 402×874 普通 WebGL 在草地、路线和密集特效上的实际光栅为准，不以名义字号或编辑器预览代替。
- **已定**：飘字合并资格服从权威逻辑时点，动画生命周期属于本地表现时间；暂停冻结表现，2 倍速仍保留最低真实阅读时间。高密度战斗先通过同目标合并、同技能同逻辑帧至多三条伤害轨道、普通信息预算、优先级替换和有限错层控制展示量，不通过无限增加同屏记录或简单把动画加速一倍处理；致死伤害不重复跳数，同帧击败合并为数量短句，并占用独立于三条伤害轨道的紧凑终结展示带。
- **已定**：飘字以命中或击败事件坐标为权威锚点，活目标只在短接触阶段跟随，随后脱离并进入紧凑错层和上浮；合并不得重新开始跟随，多目标同帧击败使用事件位置质心。锚点、错层和回弹只属于表现，不得回写目标位置、碰撞或命中判定。
- **已定**：飘字使用由项目正式中文字体与有限字形清单在编辑器中通过 SDF 确定性烘焙出的单张静态 RGBA 图集；实心填充、连续中性描边和缩放质量在离线烘焙时定型，高频短文案允许作为同图集内的有限组合词元以降低割草场景提交数。运行时只按语义角色统一着色和绘制，不得扩图、使用系统字体回退、创建逐条材质或引入第二套字体渲染路径。真实 WebGL 的最终光栅质量与帧时、稳态分配同为门槛。
- **已定**：全局震屏只服务于经过审核的重击、密集击败聚合和终局级事件。普通伤害、持续伤害、资源、常规状态和单个普通敌人击败依靠局部闪白、挤压、后坐、特效与跳字反馈；多个震屏请求不得叠加，只保留一个有冷却、可被更高语义优先级替换的低振荡节拍，暂停冻结且 2 倍速不得成倍提高真实时间内的震屏密度。

## 3. 游戏循环

### 3.1 目标大循环

`活动获取道具 → 成长页装备/养成 → 主页选择玩法并确认生效成长 → 波次战斗 → 结算 → 返回主页或再次挑战`

- **当前基线**：Lobby 已提供主页、活动和成长组成的共享局外页面壳；主页提供三张可选关卡、实际生效成长预览与开战，活动提供常驻一次性奖励领取，成长提供装备装配/强化和养成强化。战斗完成后进入结算，结算显示本局关卡，并可返回主页或以冻结的成长输入重试。
- **已定**：大厅作为共享局外页面壳，主页、活动和成长都留在 Lobby 内部切换；成长下包含装备、养成等明确子域，不把这些页面扩张为新的应用场景路线。
- **已定**：活动是局外道具来源，成长页消费或装配这些道具形成战斗强化；每个玩法显式规定允许带入的成长域、属性和上限，主页在开战前展示实际生效与被抑制的内容。
- **已定**：开战时把本次允许生效的成长解析为不可变输入并固定到会话身份；进行中的战斗不读取实时玩家资料，资料变化不能反向改变已经开始的战斗。
- **方向**：以一个真实可领取、可强化、可带入战斗并能完成结算返回的最小闭环作为扩展基础，再逐项增加装备、养成和活动内容，不交付只有入口和占位状态的空循环。
- **待定**：成长的长期重置与上限、失败收益、每日/周期活动、长期内容解锁和投放节奏。

### 3.2 单局循环

`获取/刷新资源 → 选择水果 → 种植与调整 → 配置装备 → 开始波次 → 获得波次反馈或奖励 → 下一轮准备`

当前操作包括刷新五株水果、花盆种植、水果移动、占用位置交换、同种同星合成、装备安装和花盆扩建。水果拖入已被占用的花盆或刷新栏槽位时，同种同星且未达到最高星级的组合优先合成，其他组合直接交换双方位置并保留各自身份、星级和装备；战斗期交换要求双方都通过移动冷却检查。未来增加的新操作必须说明它发生在准备期、战斗期还是结算期，避免同一动作跨越多个阶段产生歧义。

## 4. 战斗策划

### 4.1 当前基础内容

- 五种水果：豌豆、西瓜、香蕉、榴莲和向日葵，分别覆盖单体、范围、穿透、近战范围和资源生产定位。
- 四类敌人：普通、快速、装甲和首领，用于形成速度、耐久和波次压力差异。
- 三种装备：机枪、冰块和辣椒，通过兼容关系、附加技能或技能修改形成组合。
- 三套首批可选关卡组合：`orchard-01` 是 15 波 U 形教学关，`orchard-02` 是强调快速与装甲敌人的 S 形覆盖关，`orchard-03` 是以首领终局压力为重点的短核心走廊关。
- 每套关卡分别组合地图、波次、规则和表现主题；生命、阳光、波间准备、暂停、倍速和阶段奖励由所选关卡规则明确提供。
- 花盆既是种植位置，也是局内扩建资源；水果可以在刷新栏与花盆之间移动、交换或合成，满足合成条件时合成优先于交换。

这些数量是当前内容基线，不是长期内容上限。新增水果、敌人、装备和波次必须通过版本化内容定义进入，并保持已有稳定 ID 的兼容性。

### 4.2 组合边界

- 水果负责基础角色与主要技能。
- 水果、装备和敌人的主动、周期与事件反应能力统一使用有限 Ability 定义；装备只能授予已支持的 Ability，或按经过验证的稳定 ID、标签和有限属性修改明确目标，不维护独立的技能与被动执行体系。
- Ability 的激活、拥有者条件、目标、释放时序、投递方式和结果效果必须是有限、可验证且确定性的集合；配置不得执行任意脚本或构造无限嵌套效果图。
- 攻击蓄力、释放和恢复使用固定逻辑步时序。会影响结果的伤害、状态和资源必须在权威释放或命中时点结算；表现层不得通过延迟动画伪造另一个接触时点。
- 表现层只消费技能阶段、投射物命中、伤害结算、状态变化、资源与击杀等语义战斗事件，不拥有伤害、目标选择、控制、资源或胜负规则，也不得把特效种类、素材、颜色、音效和震动参数写回战斗状态。
- 新机制如果需要新的执行规则，应先通过独立 OpenSpec 变更定义边界和验收，不能用内容配置绕过规则审查。

### 4.3 关卡差异与待定战斗问题

- **已定**：关卡以稳定的 `levelId` 组合独立的地图、波次集、规则集和表现主题；战斗开始后固定整套组合身份，不允许静默回退到默认关卡。
- **已定**：地图是一个版本化聚合，内部分离三类职责：表现布局只描述语义地表与视觉标识，玩法拓扑描述地块能力、碰撞通道和有序路线，点位层描述刷怪、路线目标、核心、初始花盆候选、道具和触发位置。三类数据可以共用格子坐标，但不能互相替代或反向推导玩法规则。
- **已定**：地块玩法能力允许有限、可验证的组合，不再用一个互斥角色同时表达种植、通行、碰撞和特殊地点；碰撞是确定性的格子规则，不以 Unity 物理、Tilemap 图形或地表图片作为战斗权威。
- **已定**：地图路线以具有稳定 ID 的连续有序格子定义，入口和出口由路线首尾得到；刷怪点、路线目标和核心使用具有稳定 ID 的类型化点位表达。路线、点位、核心、花盆和单位都按同一方格投影，不能使用一张长路线图随屏幕拉伸，也不能维护第二套独立坐标。
- **已定**：地图表现保存草地、泥土、石板等语义地表，表现主题再把语义地表解析为具体 Dual-Grid 图块与底图；表现变化不改变种植合法性、怪物路线、碰撞或确定性结果，具体图块掩码由地表布局自动推导。
- **已定**：可玩地图必须通过正式关卡地图编辑器维护同一个有界、版本化地图聚合；玩法拓扑、路线与点位、地貌表现虽然分工作区编辑，但共享同一格子坐标和 `mapId`，不能由地貌素材、Tilemap 图形或独立演示板代替可玩地图数据。
- **已定**：地图制作采用“玩法拓扑 → 路线与点位 → 地貌表现 → 完整校验 → 实战预览 → 发布”的顺序。表现层可以显式读取玩法拓扑生成可撤销的推荐外观，但表现结果不得反向成为玩法授权。
- **当前基线**：战斗运行时支持单位绑定稳定命名路线，并允许同一地图中的多条路线按同一格子投影并行执行；首批三张正式地图仍各使用一条主怪物路线、一个刷怪点、一个路线目标和一个核心。首个多路线消费者是仅限编辑器与 Development Build 的八路 GM 压力测试关，不属于正式关卡、成长或结算内容，也不代表已授权制作玩家可玩的多路线关卡。可种植区域显示草地、怪物路线显示石板、其余区域显示泥土；运行时道具刷新和触发器行为仍需独立变更授权。

- 一局的目标时长与每波目标时长。
- 刷新、覆盖、合成和扩建的资源压力如何分配。
- 首领波、精英敌人和特殊事件在一局中的密度。
- 胜利、失败、中途退出和重试分别产生什么结算结果。

## 5. 大厅、结算与长期系统

- **当前基线**：Lobby 已作为由共享顶栏、页面内容区和固定底部导航组成的局外页面壳运行。主页可选择 `orchard-01`、`orchard-02` 和 `orchard-03`，选择会保存到本地资料；活动提供常驻一次性奖励领取，成长提供局外装备装配/强化和养成强化；设置尚无 Hub 页面或可用入口。结算展示完成关卡、结果、到达波次和剩余生命，并提供返回主页与原关重试。
- **已定**：大厅采用共享顶栏、页面内容区和固定底部导航组成的局外页面壳。一级目的地为主页、活动和成长；成长内部再组织装备、养成等二级页面，一级与二级导航必须保持清楚的视觉层级。
- **已定**：成长页中的“装备”指保存在玩家资料、在开战前参与成长解析的局外装备；机枪、冰块和辣椒仍是单局中安装到水果上的局内装备。两者使用不同的稳定身份、配置和生命周期，除非后续独立设计明确关联，否则不能互相替代或从名称推导映射。
- **已定**：主页继续拥有关卡或玩法选择与开战主操作；活动页拥有奖励预览、领取和完成状态；成长页拥有装备装配、装备强化和养成强化。页面展示只读取已提交资料，不能直接修改道具余额、等级、领取记录或装配状态。
- **已定**：活动奖励领取、道具消耗、装备装配和养成升级都是完整且不可重复的资料事务。失败时保留变更前资料，成功后统一刷新资源和成长展示，不能出现奖励重复发放、部分扣款或只改界面未落盘的状态。
- **已定**：玩法自身拥有成长准入规则。主页必须使用与开战相同的解析结果展示本玩法的生效强化、受限强化和阻塞原因；开战失败时不得静默改用空成长、默认成长或另一玩法的规则。
- **已定**：结算是局内结果与局外循环的交接面。返回主页后按当前资料重新解析成长；原关重试在没有成长编辑入口的前提下沿用上一局的成长输入，同时创建新的会话和随机种子。
- **方向**：首个活动采用不依赖可信服务器时钟的常驻一次性领取，至少提供一件可用装备和足以完成一次真实强化的材料，以证明活动、成长和战斗之间的因果关系。每日、周期和远程活动只有在时间与后台权威明确后再扩展。
- **方向**：设置及其他未来局外系统继续由大厅统一承载；未实现的入口必须明确锁定，不能伪装成可用按钮。
- **待定**：三关之后的长期关卡组织结构、后续成长内容和数值、货币种类、失败收益、每日/周期活动和内容投放节奏。

## 6. 内容生产与版本边界

- 使用 ScriptableObject 作为当前编辑入口，并导出为确定性的版本化内容数据。
- 水果、敌人、装备、技能、波次和奖励，以及关卡、地图、波次集、规则集和主题都使用语义稳定 ID；显示名称、枚举顺序或 Unity 资源 GUID 不作为运行时身份。
- 局外道具、活动、局外装备、养成节点、成长成本和玩法成长准入规则同样使用语义稳定 ID，并由同一个根游戏内容清单固定其目录身份、版本和跨目录引用；不得建立第二套根清单、生产 C# 默认值或缺失内容回退。
- 玩家资料只保存已经验证的局外内容身份、数量、等级、装配和领取记录，不复制内容定义；单局会话则固定本次成长准入规则、解析结果和指纹，不能在战斗中重新解释当前资料。
- 主动、周期和事件反应能力共用同一版本化 Ability 内容模型；投递与结果载荷分别描述效果如何到达目标和命中后发生什么，不以视觉 Cue 充当玩法效果。
- 战斗表现目录按 Ability、投射物、状态和击杀等稳定玩法身份映射独立反馈配置。生产内容可能产生的反馈必须有明确配置或明确的无反馈策略，不允许因为映射缺失而静默套用通用特效。
- 地图中的语义地表、路线、点位和点位分组使用稳定 ID；地图仍以一个聚合内容单元管理三类职责，不拆成彼此可独立漂移的多份运行时真相。
- 内容导出必须先验证引用、兼容关系和机制类型，再生成规范化结果。
- 地图编译必须验证表现与玩法网格覆盖、能力与碰撞类型、路线连续性、点位引用、同格组合和当前玩法支持范围；内容只能选择有限的已审核类型，不能通过自由属性或任意脚本自行发明执行机制。
- 玩法地图身份只包含会影响战斗的地块能力、碰撞、路线和点位；语义地表、表现主题、图块与其他纯视觉信息单独归入表现身份，纯视觉调整不得改变战斗快照、确定性校验或结果。
- 单局从开始到结算固定会话 ID、随机种子、内容版本和完整关卡组合身份，不能在战斗中静默切换内容。
- 远程内容可以在后续版本替换目录或资源包，但不能成为任意运行时代码热替换通道。
- 编辑器版本、SDK 版本、构建哈希和当前产物大小属于发布证据，不属于策划总纲。

### 6.1 地图制作与发布流程

- **已定**：地图制作拆分为两个边界明确的工具。地貌素材实验室只维护底图、透明地貌、定向精修边缘和 Dual-Grid Mask 等美术与渲染素材，不生成可玩关卡，也不作为地图可发布的证据；关卡地图编辑器是制作可玩地图的正式入口。
- **已定**：关卡地图编辑器在同一有界俯视画布上提供玩法格、路线与类型化点位、地貌表现、校验与发布工作区。日常制作只暴露有限且已审核的能力、碰撞、语义地表、边缘样式和点位类型，不要求策划直接操作原始 TileSet、Mask 或第二套坐标。
- **已定**：允许保存校验未通过的地图草稿，以便继续编辑；但网格覆盖不完整、数据越界、路线不连续、必需点位缺失、同格组合冲突、稳定 ID 重复、模板引用无效或正式地貌材质缺失时，必须阻止发布和正式实战预览，并把问题定位到具体格子、点位或引用。
- **已定**：正式发布集合由独立发布清单统一授权，清单负责发布顺序、稳定 `levelId`、模板关卡和地图之间的绑定。运行时目录只能由发布清单全量、确定性重建，不允许手工编辑生成物，也不允许从生成物反向恢复或覆盖创作数据。
- **已定**：正式 Playtest 必须先完成发布清单重建、资源保存与重新加载，再按稳定 `levelId` 进入正常 `Bootstrap → Battle → Settlement` 流程。临时内存预览、地貌验收板或绕过关卡目录的演示场景不能替代正式实战验收。
- **已定**：编辑器预览与 Battle 使用同一地图编译结果、方格投影和正式地貌材质解析规则；无需修改代码即可完成一张新地图的创建、校验、发布和实战，是关卡地图编辑能力的最低完成标准。

具体内容契约见 `openspec/changes/archive/2026-07-20-establish-versioned-battle-content-catalog/design.md`、`openspec/changes/archive/2026-07-20-introduce-composable-battle-skills/design.md`、`openspec/changes/archive/2026-07-16-refactor-battlefield-route-to-tile-grid/design.md`、`openspec/changes/archive/2026-07-16-introduce-level-map-catalog/design.md`、`openspec/changes/archive/2026-07-23-separate-battlefield-visual-topology-and-markers/design.md` 和 `openspec/changes/build-canonical-battlefield-map-editor/design.md`。

## 7. 版本方向

### P0：完整基础闭环

形成可重复验证的 `Bootstrap → Lobby → Battle → Settlement` 流程，完成确定性战斗、版本化内容、本地轻量资料、战斗快照契约和 WebGL 竖屏验收。P0 的实时完成状态以 [P0 发布基线](../p0-release-baseline.md) 为准。

### P1：平台与交付能力

先证明抖音小游戏的导出、转换、模拟器、真机、生命周期、资源交付和稳定性，再进入正式运行时适配；微信小游戏在抖音路径稳定后推进。账户、云端资料、远程内容和代码包更新只有在相应门禁通过后才能立项。实时状态见 [P1 首波门禁](../p1-first-wave-gate.md) 和 [平台验证文档](../platform/)。

### 局外基础循环与内容扩展

在不改变 `Bootstrap → Lobby → Battle → Settlement` 应用路线的前提下，Lobby 已扩展为主页、活动和成长组成的局外页面壳，并已形成常驻活动领取、装备或养成强化、玩法成长准入预览、不可变成长输入开战、结算返回与原输入重试的纵向闭环。后续按独立内容计划增加装备、养成节点、活动与玩法策略；完整经济、周期运营、商业化和远程内容仍需各自的策划与门禁，不由页面框架自动授权。

## 8. 当前阶段排除项与长期架构边界

### 当前阶段不做

- 支付、广告、分享和商业化投放。
- 商店、交易、制作、随机词条、装备分解、背包容量等完整局外经济。
- 依赖可信服务器时钟的每日/周期活动、远程活动排期和正式运营后台。
- 生产账号体系、云端资料和正式后端服务。
- 未通过兼容门禁的平台 SDK、上传或生产发布。
- 自动恢复进行中的战斗。

这些是阶段性范围，不代表产品永远排除。若要纳入，应先补齐策划目标和独立 OpenSpec 变更。

### 长期架构边界

- 不允许任意运行时代码热替换或以内容配置执行未审核代码。
- 小游戏平台适配器不可静默回退为普通 Web 适配器。
- 核心战斗规则不直接依赖抖音、微信或浏览器 SDK。
- 活动奖励、道具消耗、装备装配和养成升级必须通过可验证、不可重复的资料事务提交；UI 展示不是资料权威。
- 装备和养成只能贡献有限、已审核的成长属性。玩法通过显式准入规则决定可带入域、属性和上限，内容配置不能借成长系统执行任意脚本或建立第二套战斗属性执行器。
- 战斗只消费开战时冻结的成长输入；运行中的战斗、快照恢复和结算重试不得静默改读当前资料或替换成长身份。
- 当前没有 PVP、跨玩家同步或强反作弊需求，因此不引入服务端权威战斗；若这些前提变化，应重新做架构决策，而不是把当前结论解释为永久禁止服务端能力。

## 9. 待定策划决策

| 主题 | 需要决定 | 应在何时决定 |
|---|---|---|
| 单局时长 | 目标时长、波数区间、准备期占比 | 扩展第二套正式关卡前 |
| 关卡结构 | 首批三关之后，线性关卡、章节地图、无尽模式的主次关系 | 扩展首批三关前 |
| 后续成长内容 | 新增局外装备槽位、养成节点、可带入属性、各玩法准入范围与上限 | 扩展当前基础成长内容前 |
| 长期成长深度 | 长期成长对象、重置、上限、追赶与内容淘汰规则 | 扩展首批成长内容前 |
| 失败收益 | 无收益、保底收益或按进度结算 | 接入正式奖励前 |
| 经济结构 | 货币数量、来源、消耗和防通胀边界 | 实现商店或多资源经济前 |
| 活动运营 | 每日/周期活动是否进入首发、可信时间来源、重置与补发规则 | 实现周期活动前 |
| 内容节奏 | 水果、装备、敌人、关卡、成长和活动的投放频率 | 制定首个内容版本计划前 |
| 商业化 | 广告、付费和分享是否进入产品范围 | 平台正式发布方案确定后 |

每个待定项形成决策后，应先提醒用户该决定会影响哪些策划章节，并询问是否同步本总纲。只有用户明确确认后才能更新；具体实现仍需进入对应的 OpenSpec 变更。
