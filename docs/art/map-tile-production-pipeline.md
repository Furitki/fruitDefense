# 地图图块统一生产管线

本文是 FruitDefense 后续地图图块设计、生成、审核、生产化、关卡接入和实机验收的唯一总入口。纯方块基层与 Dual-Grid 共用本文的阶段和门禁；两者只在候选拆分、连续性证明和 Unity 资产结构上分支。

目标不是让一张独立图块“看起来不错”，而是稳定获得与现有清爽果园风格协调、在真实方格地图中连续、进入目标关卡后仍然好看的结果。

若其他地图图块文档与本文冲突，以本文的阶段顺序、审核边界、资产隔离和发布门禁为准。Dual-Grid 的具体拓扑、Mask、脚本和压力图规则由 [Dual-Grid 地图图块生成技术分支](dual-grid-tile-generation-pipeline.md) 继续负责。

## 1. 不可跳过的总流程

```text
锁定目标关卡、地形语义与表现类型
  -> 生成差异充分的风格方向候选
  -> 人工选定方向（例如 S1）
  -> 制作真实方格地图的游戏内预演
  -> 第一次人工门禁：批准整体配色、质感、格子节奏和游戏内观感
  -> 在 Evidence/Trials 中完成候选拆分、归一化和连续性验证
  -> 制作使用最终候选图块的真实运行时地图
  -> 第二次人工门禁：批准最终平铺、边界、玩法可读性和 UI 协调性
  -> 提升为生产资源并绑定独立 Palette
  -> 聚焦 Smoke、全量 Smoke、普通 WebGL 构建
  -> 从 Bootstrap → Lobby → 目标 Battle 的真实竖屏画布截图验收
```

第一次人工门禁之前，不得把候选当成正式图块；第二次人工门禁之前，不得进入发布依赖图。机械 QA、模型返图、独立图块预览或普通构建成功都不能替代这两次视觉门禁。

候选处理为了制作预演可以在 `Builds/Evidence` 或 `Assets/.../Trials` 中生成临时切片或 Mask；这不算正式拆分和实装。用户批准后，才允许从已批准候选确定性地产生或复制生产资源。

## 2. 第一阶段：锁定设计输入

开始生成前必须明确记录：

- 目标关卡、地图尺寸、主要地形分布和支持的竖屏视口；
- 每种材质的语义 ID，而不是“绿色块”“棕色块”等临时名称；
- 使用 `BaseOnlySquare` 还是 `DualGrid`；
- 哪些现有游戏截图、批准稿或生产色板是视觉权威；
- 本轮只改哪些关卡，哪些关卡必须保持不变；
- 不允许改变的玩法数据：路线、种植区、核心、标记、投影、命中和模拟结果。

没有明确目标地图的“通用素材图”不能直接进入生产。地图尺寸和地形分布未知时，只能做风格探索，不能宣称可接入。

### 2.1 表现类型选择

| 类型 | 适合情况 | 核心结构 | 连续性责任 |
|---|---|---|---|
| `BaseOnlySquare` | 清楚的棋盘感、每格独立、清爽低噪声地图 | 每个格子只有一个完整基层材质 | 每张图块自身可平铺；相邻格不依赖额外边缘图 |
| `DualGrid` | 需要有机地貌轮廓、材质覆盖和方向性边界 | 基层 + 可选地貌 + 轮廓 + 可选有向边缘 | 完整 16 Mask、socket、合法邻接和压力图共同负责 |

类型必须写入 canonical map 的视觉格数据或明确的创作配置。禁止由渲染器根据关卡 ID、纹理路径、颜色或缺失资产猜测类型。

## 3. 统一视觉规则

### 3.1 风格基线

- 总体方向为清爽、明亮、卡通、轻手绘，不追求写实材质扫描感。
- 使用大块面和低频纹理；避免细碎噪点、密集颗粒、尖锐高频划痕和过度锐化。
- 草地、泥土、石路、水面等必须来自同一套光照方向、明度区间、饱和度逻辑和笔触尺度。
- 优先与游戏现有奶油纸面、嫩绿操作色和暖黄强调色协调，不孤立追求素材本身的高饱和或强对比。
- 格线属于地图交互与投影层，不得画进地表纹理。
- 玩法单位、花盆、路线提示和状态反馈必须比地表更容易识别；地形不能成为第一视觉焦点。

### 3.2 候选差异

一轮风格探索应提供方向差异充分的候选，而不是只改少量色相或纹理随机种子。可拉开的维度包括：

- 笔触概括程度；
- 色温与明度关系；
- 纹理密度；
- 卡通轮廓强弱；
- 草地与泥土的对比方式。

每个候选必须有稳定版本名和对应提示词。用户选定的方向成为本轮唯一视觉权威；后续拆分和导入不得擅自调色、补纹理或混入未批准候选。

## 4. 游戏内方格预演门禁

风格图之后必须制作“游戏内方格地图版”预演，不能只展示素材表、双瓦片拼图、单格放大图或脱离 UI 的平铺墙。

预演至少满足：

- 使用目标地图的真实行列数、草地/道路分布和格子比例；
- 使用目标竖屏视口或等价的游戏内页面构图；
- 显示真实格线、舞台边框以及足以判断层级的 Header/控制区环境；
- 按游戏内缩放展示，不用局部放大掩盖整体问题；
- 不绘制会被误拆进图块的单位、文字、网格或装饰；
- 对比现有 UI 的色温、饱和度和明度，明确检查地图是否“贴进去”而不是“浮出来”。

第一次人工门禁只回答整体方向是否成立。出现以下任一问题就返回风格阶段，不进入正式拆分：

- 纹理太细、太写实或缺少卡通手绘感；
- 草地与泥土来自不同光照或不同色板；
- 地图比 UI 更脏、更暗、更艳或更重；
- 方格节奏断裂、边缘噪声抢眼；
- 只有单图好看，组合地图不好看。

## 5. 纯方块基层分支

### 5.1 生产结构

- 一个文件只表达一种完整方形地表，不生成左右拼接或“草地＋泥土”双瓦片作为 Runtime 输入。
- 当前生产基准为 `64×64`、完全不透明、FullRect、64 PPU、Repeat、Bilinear、无 Mipmap、无压缩；规格升级必须形成新版本并重新验收。
- 草地格直接使用草地基层，泥土格直接使用泥土基层。
- `LandformSurfaceId`、`ContourStyleId` 和 `EdgeStyleId` 必须为空；纯方块不能偷偷叠加 Dual-Grid 遮罩修边。
- 每张图块必须独立成立，不能依赖相邻格补齐阴影、边缘、图案或光照。

### 5.2 连续性检查

至少检查：

- 同材质横向、纵向和大面积重复；
- 草地与泥土交界时是否出现双亮边、双暗边或假立体墙；
- 四角相接时是否形成明显十字或亮点；
- 真实地图缩放下是否出现重复花纹、摩尔纹或高频闪烁；
- 单格边缘像素、wrap、filter 和压缩是否与生产导入契约一致。

纯方块的连续性来自完整基层，不通过生成额外过渡块掩盖问题。基础纹理本身不合格时应回到候选阶段。

## 6. Dual-Grid 分支

Dual-Grid 候选同样必须先通过本文的风格方向和游戏内方格预演门禁。其候选 Mask、图集和压力图在批准前全部属于 Evidence，不得因为 16 Mask 已生成就直接导入生产。

获批方向按 [Dual-Grid 地图图块生成技术分支](dual-grid-tile-generation-pipeline.md) 完成：

- A/B 拓扑路线选择；
- Raw、Normalized、Review256、Runtime64 和 Runtime32 的确定性派生；
- 完整 `Mask-00..15` 与 socket 验证；
- 横纵合法邻接穷举、压力图和真实 mismatch 记录；
- `BrushImport.json`、`TerrainBrushDefinition` 和生产 TileSet 导入。

`seamSafetyClaimed=false` 不能被机械通过、人工喜欢或普通 WebGL 成功自动改写。第二次游戏内门禁仍必须检查最终 Runtime Mask 在真实目标地图中的轮廓连续性。

## 7. 两套表现的兼容约束

- 两套表现共用同一个 canonical battlefield aggregate、`BattlefieldProjection`、玩法格、路线、标记和命中几何，不建立第二套地图坐标源。
- 一个地图或连通地貌区域必须显式选择表现类型。
- 同一种 semantic surface 如果共享边或顶点，不得一部分用纯方块基层、一部分用 Dual-Grid landform 表示。
- 两套表现可以用于不同关卡，或用于彼此断开的地貌区域。
- Palette 必须按稳定语义 ID 解析；缺失精确材质、轮廓或有向边缘绑定时明确失败，不回退到另一套表现。
- 不覆盖全局默认 Palette 来试验单关效果。每个获批的关卡视觉变体使用独立 Palette ID，未批准关卡保持原样。
- Palette 保持完整生产绑定；完整不等于允许回退，运行时仍只使用地图明确请求的绑定。

## 8. 资产隔离与提升

### 8.1 审核资产

以下内容只属于 `Builds/Evidence` 或 `Assets/.../Trials`：

- 风格候选、提示词、模型调用记录和 provenance；
- 整图预演、比较板和审核标注；
- 候选切片、临时 Mask、压力图和失败证据；
- 尚未通过第二次人工门禁的 Unity 试验场景或 Palette。

### 8.2 生产资产

批准后将最终候选确定性地复制或派生到生产目录，并记录：

- 稳定语义 ID、资产路径和 Unity GUID；
- 源候选与生产文件的 SHA-256；
- 尺寸、PPU、Filter、Wrap、Compression、MipMap 和 alpha；
- Palette、TileSet、关卡 Theme 和 Battle 场景的绑定关系。

正式 Battle、发布场景、`Resources` 和可玩目录不得依赖 Trials、提示词、provenance、审核母图或试验 Palette。生产文件不得在提升后继续手工修图；需要修改时创建新候选并重新走完整流程。

## 9. 关卡接入约束

1. 只绑定用户批准的目标关卡；其他关卡保持当前 Palette 和视觉构成。
2. 视觉格变化不得改变 gameplay fingerprint、路线、植物可放置格、核心、标记、投影、命中或确定性模拟结果。
3. Theme 通过稳定 Palette ID 选择表现；场景注册所有被发布目录引用的 Palette。
4. 不在 Presenter 或 renderer 中加入关卡 ID 特判、纹理路径判断、fallback 或迁移兼容层。
5. 先在单关端到端跑通，再逐关批准和扩展；一次审核不自动授权全局替换。

## 10. 必须完成的验证

### 10.1 机械与编辑器验证

- 源候选、生产图块和 manifest 的 hash/尺寸/alpha 一致性；
- Unity import 参数、Sprite/GUID、Palette/TileSet 精确绑定；
- 地图每格视觉覆盖、表现类型兼容和目标格子数量；
- 目标关卡使用新 Palette，非目标关卡仍使用原 Palette；
- 正式场景和 Palette 无 Trials 依赖；
- 玩法 fingerprint、路线、标记、格子能力和确定性结果不变；
- 变更专属聚焦 Smoke；
- `FruitDefense.Editor.ProjectSetup.SmokeValidate` 全量 Smoke。

### 10.2 实机视觉验证

- 使用普通发布基线的 WebGL 构建，不以隔离试验构建代替；
- 从 `Bootstrap → Lobby` 选择目标关卡，再进入真实 `Battle`；
- 在 402×874 参考视口取证，并按风险补充 360×800、375×812、430×932；
- 截图必须包含完整地图、Header 和操作区，以便同时判断配色、层级和玩法可读性；
- 检查缺图、接缝、重复纹理、格线、边缘、单位遮挡、safe area 和 palette 诊断；
- 保存构建日志、截图路径、SHA-256 和已知平台能力限制。

普通 WebGL 通过只证明共享发布基线；不能据此声称抖音或微信转换成功。

## 11. 失败与返工规则

出现以下情况必须退回对应阶段：

- 方向不协调、纹理太细、不够卡通或不够清爽：回到风格候选；
- 整图预演不成立：调整配色和笔触后重新预演，不能先拆图再赌组合效果；
- 候选拆分后出现接缝或拓扑问题：回到候选/拆分阶段，不在生产资源上局部补丁；
- 实机与批准预演明显不同：检查投影、导入、Palette 和缩放，修正后重新走第二次人工门禁；
- 玩法 fingerprint 或命中变化：停止发布并修复 canonical map 接入；
- 只有机械 QA 通过但没有人工批准：保持 Evidence 状态。

禁止通过模糊、加噪、画死格线、增加黑边、静默调色、运行时叠色或 Palette fallback 掩盖问题。

## 12. 当前批准参考

第一关 `orchard-01` 是纯方块基层分支的参考实现：8×7 地图由 35 个 base-only 草地格和 21 个 base-only 泥土格组成，使用独立 `palette.orchard-01.square-grid`，第二、三关继续使用原默认 Palette。

正式资源位于：

```text
Assets/Battlefield/Terrain/Orchard01SquareGrid/
```

具体实现与验收合同见：

```text
openspec/changes/apply-square-terrain-to-first-level/
```

该参考锁定的是流程、表现结构和批准后的生产像素，不授权后续关卡直接复制第一关配色。每个新主题仍需重新完成游戏内预演和两次人工门禁。
